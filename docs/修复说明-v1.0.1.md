# 公众号HTML插入助手 — 插入链路修复说明（v1.0.1 → v1.0.2）

日期：2026-09-25　｜　版本：v1.0.0 → v1.0.2（两轮 PATCH）

## 1. 问题现象

**第一轮（v1.0.0 → v1.0.1）**

1. 首次使用必须先点「读取」把编辑器内容载入，「插入到编辑器」才生效；直接插入无反应。
2. 「读取」后再插入，公众号正文出现标签错乱，插入的代码呈乱码。

**第二轮（v1.0.1 → v1.0.2）**

3. 插入位置错乱：内容跑到文章开头或错误层级，把页面原有的标签结构顶坏。

## 2. 根因分析

| # | 根因 | 对应现象 |
|---|---|---|
| A | 公众号正文 DOM 由 **ProseMirror 托管**。原来直接 `appendChild` / `insertNode`，属于「外部 DOM 变更」。PM 会用自身 state 重新渲染把变更抹掉，或在 `readDOMChange` 解析失败时产出畸形结构 | 第一次插不进去；插入后标签错乱 |
| B | 「读取」拉进来的是**整篇正文**，而插入是**追加到末尾**语义，两者叠加 = 文章被复制一份 | 内容重复、嵌套标签错乱 |
| C | `sanitizeForWeChat` **无条件**用 `DOMParser` 做 parse → serialize 往返。`&nbsp;`、内联 SVG、`mpvoice` 等 `mp-*` 自定义标签、嵌套 table 会被改写；已是 `&amp;` 的实体被二次转义成 `&amp;amp;` | 乱码 |
| D | **DOM 选区与 PM 内部 selection 的同步是异步的**。`buildInsertRange` 只改了 DOM 选区，而 PM 的 paste / `replaceSelection` 用的是它 state 里的 selection；`selectionchange` 由浏览器异步派发，设完选区立刻 dispatch paste，PM 读到的还是旧 selection（编辑器从未 focus 过时通常停在 doc 开头） | **插入位置错乱** |

### A 的补充说明

之前「先读取才插得进去」并不是读取本身的功劳，而是这个动作前后用户通常已经点过正文区域、编辑器进入激活态。真正的必要条件是 **ProseMirror view 处于可接收变更的状态**。

### D 的补充说明（第二轮重点）

设完选区后立刻写入，时序上是这样的：

```
sel.addRange(range)          // 只改了 DOM 选区
editor.dispatchEvent(paste)  // 同步执行 —— 此时 PM 还没收到 selectionchange
                             // → PM 用的仍是旧 selection → 插到错误层级
... 浏览器随后派发 selectionchange，PM 才同步
```

## 3. 修复方案

### 3.1 走 ProseMirror 官方变更通道（`content.js`）

插入流程：**focus 激活 → 定位光标 → 等选区同步 → 三级通道 → 结果校验**

```
targetEditor.focus()                     // 让 PM view 进入激活态
  → buildInsertRange(editor, mode)        // replace=全选 / 有选区=选区 / 否则=末尾
  → primeEditorSelection()                // 【v1.0.2】应用选区 → 等两拍 → 校准
  → insertViaPaste()                      // 通道一：paste 事件，PM 用自身 clipboard parser 做 schema 转换
  → insertViaExecCommand()                // 通道二：document.execCommand('insertHTML')
  → insertViaDom()                        // 通道三：裸 DOM，仅兜底
  → 校验：unchanged（未生效）/ appendedAtTail（位置错）/ true
```

- paste 通道被 `preventDefault` 即视为 PM 已接管，直接信任其解析结果；
- execCommand / 裸 DOM 通道比对插入前后 `innerHTML`，无变化返回 `unchanged`；
- 追加模式用 `appendedAtTail()` 校验内容确实落在文末，否则返回 `misplaced`；
- `unchanged` / `misplaced` 时弹窗**都不关闭**，给出对应提示，避免用户以为没成功而重复插入。

### 3.2 选区同步（v1.0.2 核心）

```js
async function primeEditorSelection(sel, range) {
  applyRange(sel, range);
  await nextTick(); // 浏览器派发 selectionchange，编辑器读取并同步其 state
  await nextTick(); // 编辑器可能回写选区，再等一拍
  applyRange(sel, range); // 校准回目标位置后立刻插入
}
```

⚠ **不能用「选区是否完全相等」判断同步成功**：PM 同步完成后会把选区**规范化回写**到等价但未必全等的位置（例如把 `editor/offset=N` 映射到具体文本节点），精确比对会 100% 误判。所以改为固定等待 + 写入前校准。

### 3.3 拆分「读取」与「插入」的语义（v1.0.1）

- 新增 `insertMode`：`append`（默认）/ `replace`；
- 底部新增切换按钮 `#wx-ext-btn-mode`（「追加末尾」/「替换整篇」），插入按钮文案与 title 同步；
- 点击「读取」后自动切到 `replace`，`replace` 走全选 + 插入 = 整体替换，不再复制一份。

### 3.4 净化不再无条件重写 DOM（v1.0.1）

```js
const RISKY_NODE_RE = /<\s*(script|iframe|object|embed|link|meta|base|form)\b/i;
const RISKY_ATTR_RE = /[\s"']on[a-z]+\s*=/i;
```

- 未命中风险内容 → **原样返回**，保证「读进来再插回去」是恒等操作；
- 命中 → 才做 `DOMParser` 清理；
- 标签开合检查抽为纯文本逻辑 `collectTagBalanceWarnings()`，不触碰 HTML 本体。

### 3.5 编辑器命中徽标（v1.0.2 诊断能力）

弹窗标题旁显示 `编辑器 #N · X 字`，悬停看命中的元素路径；若该级选择器命中多个元素（可能同时存在预览副本、摘要框等 `contenteditable` 实例），徽标变黄警告。用于快速判断"操作的是不是正文编辑器"。

## 7. 通用教训（已写入 AGENTS.md）

1. **托管型富文本编辑器（ProseMirror / Slate / Lexical）禁止直接改 DOM 插入内容**，必须走其原生变更通道（paste 事件 / execCommand），裸 DOM 仅兜底。
2. **DOM 选区与编辑器内部 selection 的同步是异步的**，写完立刻触发变更必踩坑；同理，任何「写完马上读回比对」的校验都要考虑编辑器自己的规范化回写。
3. **不要对已合法的 HTML 做无条件的 parse → serialize 往返**，会改写实体与自定义标签。
